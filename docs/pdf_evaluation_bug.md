# Bug: `--incoming q` / `rp.incoming=="q"` read an uninitialized PDF flavor

This may have affected results in 2310.06640

## Summary

`PdfSet::xf()` ([src/pdf_set.cpp](../src/pdf_set.cpp)) selects which LHAPDF
flavor to evaluate by string-comparing `rp.incoming` against `"g"`, `"d"`,
`"u"`, `"s"`, `"dbar"`, `"ubar"`, `"sbar"`. There was no `"q"` branch, even
though:

- the CLI's own usage text ([src/cli.cpp](../src/cli.cpp)) lists `--incoming
  <g|q|u|d|s|ubar|dbar|sbar>` as valid,
- channel selection in [src/params.cpp](../src/params.cpp) treats any
  `incoming != "g"` as "the quark channel" (`Channel::QQ`/`Channel::QG`),
  which invites passing `"q"` directly rather than a specific flavor, and
- the repository's own top-level `reference_run_command` does exactly
  that: `./build/nlosingleinclusive 0.4 0.95 0.5 pp 0 q q mom 2 1`.

So `rp.incoming == "q"` fell through every `if`/`else if` and left the
local `int particle_flag` **uninitialized**, which was then passed straight
to `LHAPDF::PDF::xfxQ2(particle_flag, x, Q2)` — undefined behavior, not "sum
over quark flavors."

In practice this was **not** random per run: the same compiler/binary lays
out that stack slot the same way every time, so it silently produced a
fixed, wrong, but *reproducible* number — which is exactly why it went
unnoticed and even got enshrined as a "golden" reference value (see
"Provenance" below).

Contrast with `FfSet::zD()` ([src/ff_set.cpp](../src/ff_set.cpp)), which
handles the equivalent case correctly: `rp.outgoing=="q"` sums the
fragmentation function over all `Nf` light quark flavors and their
antiquarks. `PdfSet::xf()` had no equivalent summing branch on the incoming
side at all.

## Provenance: not a refactor regression

Checked against `utils.cpp` at commit `9d4372793c353df5814052d203e06550aec4e795`
(pre-refactor, original monolithic code) — the same branch chain, the same
missing `"q"` case, the same uninitialized `particle_flag`:

```cpp
// utils.cpp @ 9d43727
int particle_flag;
if(incoming.compare("g")==0) particle_flag = 0;
else if(incoming.compare("d")==0) particle_flag = 1;
else if(incoming.compare("u")==0) particle_flag = 2;
else if(incoming.compare("s")==0) particle_flag = 3;
else if(incoming.compare("dbar")==0) particle_flag = -1;
else if(incoming.compare("ubar")==0) particle_flag = -2;
else if(incoming.compare("sbar")==0) particle_flag = -3;
return lhpdf->xfxQ2(particle_flag,x,Q2);
```

This confirms the bug predates the modular `src/` refactor entirely — it was inherited unchanged. 

## Impact on the regression suite

Half of `tests/regression/cases/` used `incoming q` and were therefore
built on the same artifact:

| Case | incoming | outgoing | Affected? |
|---|---|---|---|
| `pp_gg_*` | g | g | no |
| `pp_gq_*` | g | q | no (outgoing side was already correct) |
| `pp_qg_*` | q | g | **yes** |
| `pp_qq_*` | q | q | **yes** |

## Fix

`PdfSet::xf()` now mirrors `FfSet::zD()`: `rp.incoming=="q"` sums
`xfxQ2(flavor,...)+xfxQ2(-flavor,...)` over `flavor=1..Nf` (u,d,s and their
antiquarks), and every branch, including a genuinely unrecognized value,
either returns immediately or calls `exit(1)` with an error message — there
is no longer a fall-through path that leaves anything uninitialized.

`tests/regression/cases/{pp_qg,pp_qq}_{fixed,mom}/golden.csv` were
regenerated by re-running each case's `args` against the fixed binary. LO
was already `0` for the `pp_qg_*` cases before and after (that's a genuine
feature of the LO qg channel, not related to this bug); the `pp_qq_*` LO
values moved from the old artifact (`0.000550629`) to a real
quark-flavor-summed value (`0.0051852`) — roughly a factor of ~9.4, in line
with summing 6 quark+antiquark flavors instead of reading one uninitialized
slot. All 8 regression cases pass against the regenerated goldens.

### Before/after: the numbers actually moved, not just cosmetically

Format below is `z,k,LO,NLO` (matching the program's CSV output). "Before"
is the pre-fix golden.csv (the uninitialized-`particle_flag` artifact),
"after" is the regenerated one:

**`pp_qg_fixed`** (incoming=q, outgoing=g, fixed coupling):
```
before: 0.95,2.10526,0,0.000165085
        0.45,4.44444,0,1.47682e-05
after:  0.95,2.10526,0,0.00359783
        0.45,4.44444,0,0.000365859
```
NLO moved by roughly a factor of ~22x (LO stays 0 in both — genuine
physics for this channel, unrelated to the bug).

**`pp_qg_mom`** (incoming=q, outgoing=g, mom coupling):

        0.45,4.44444,0,2.32631e-05
after:  0.95,2.10526,0,0.00566738
        0.45,4.44444,0,0.000576309
```
NLO moved by roughly a factor of ~22x.

**`pp_qq_fixed`** (incoming=q, outgoing=q, fixed coupling):
```
before: 0.95,2.10526,0.000550629,0.000698852
        0.45,4.44444,8.96498e-06,3.10289e-05
after:  0.95,2.10526,0.0051852,0.0067526
        0.45,4.44444,9.31988e-05,0.000340623
```
LO moved by ~9.4x, NLO by ~9.7x.

**`pp_qq_mom`** (incoming=q, outgoing=q, mom coupling):

        0.45,4.44444,9.31988e-05,0.000538155
```
LO moved by the same ~9.4x as `pp_qq_fixed` (LO doesn't depend on the
coupling scheme), NLO by ~9.7x.

So any prior quark-channel (`incoming q`) result computed with this code —
not just these golden files — was off by roughly an order of magnitude,
not a rounding-level discrepancy. Anything derived from `--incoming q`
runs before this fix (plots, fits, physics conclusions) should be
recomputed.

## Lesson

`PdfSet::xf()`'s original pattern — an uninitialized local filled in by an
`if`/`else if` chain with no `else` — has no compile-time or even
straightforward runtime signal when a case is missed; `FfSet::zD()`'s
pattern (return immediately per branch, `exit(1)` on an unrecognized value)
does. Prefer the latter for any similar flavor/channel dispatch added in
the future.
