# Regression suite

Safety net for the ongoing refactor away from the `main.cpp`
`#include`-everything unity build towards a modular, header-based design
(see the refactor plan discussed with Heikki). Run this after every stage
of the refactor to confirm the physics output hasn't changed.

## Usage

```sh
tests/regression/run.sh              # all cases
tests/regression/run.sh pp_qq_mom     # just one case
RTOL=1e-8 tests/regression/run.sh     # tighter tolerance
```

Builds via CMake, runs the binary against each case's `args`, and compares
stdout to `golden.csv` within a numeric tolerance (`compare_csv.py`) rather
than an exact text diff, since the program only prints ~6 significant
digits and later refactor stages may reorder arithmetic in ways that are
mathematically but not bit-for-bit equivalent.

Each run is slow (the NLO cross section at a single (z, k) point is
expensive) — a handful of z points per case take a few minutes. Cases
deliberately use a coarse z-step to keep this bearable.

## Cases

Every channel is run under both `mom` and `fixed` running coupling, since
those are the only two `alpha_s_running` schemes that bypass the per-term
coefficient-function branches entirely (see "Coupling-scheme guard" below)
and so are guaranteed not to hit the `smallest`/`daughter` gaps documented
in [`../../docs/PAPER_MAPPING.md`](../../docs/PAPER_MAPPING.md).

- `pp_qq_{mom,fixed}`: proton-proton, quark-in/quark-out channel
  (`with_CF`/`with_Nc`, `I2`/`J`/`Jv` coefficient functions). Mirrors the
  original ad hoc `reference_run`/`reference_run_command` at the repo root
  (same command, current z-range/momentum).
- `pp_gg_{mom,fixed}`: proton-proton, gluon-in/gluon-out channel —
  exercises the `with_gg` code path (`H2`/`H3`/`H4` coefficient
  functions) that `pp_qq_*` never touches.
- `pp_qg_{mom,fixed}`: proton-proton, quark-in/gluon-out channel —
  exercises the `with_gl` code path (`K1` coefficient function).
- `pp_gq_{mom,fixed}`: proton-proton, gluon-in/quark-out channel —
  exercises the `with_gq` code path (`K2` coefficient function).

## Coupling-scheme guard: `test_alpha_s_guard.sh`

```sh
tests/regression/test_alpha_s_guard.sh
```

Separate, near-instant script (no golden output involved) that locks in
`params::validate_alpha_s_running`'s rejection of `alpha_s_running`
choices that are incomplete for a given channel — see
[`../../docs/PAPER_MAPPING.md`](../../docs/PAPER_MAPPING.md), "Known
coupling-scheme gaps".

## Known gap: no pA case

`col=pA` is currently **broken** in this checkout: `params::bksolpA` in
[`../../src/params.hpp`](../../src/params.hpp) points at the same single
`./KCBK_fit_3/proton.dat` file used for `pp`, but the pA-loading code in
[`../../src/dipole_amplitude.cpp`](../../src/dipole_amplitude.cpp) appends
a digit derived from `b` *after* the `.dat` extension, expecting
per-impact-parameter files (e.g. `Pb_b_0`) that don't exist in
[`../../KCBK_fit_3/`](../../KCBK_fit_3/). Any `col=pA` run currently exits
1 with `Error opening the BK solution file`. Add a `pA` case here once
that's fixed (either point `bksolpA` at real `Pb_b_*` files, or adjust the
naming logic to match what's actually on disk).

## Adding a case

Create `cases/<name>/args` (one line, space-separated argv — everything
after the executable name) and `cases/<name>/golden.csv` (trusted output,
generated by running the pre-refactor binary). `run.sh` picks up any
directory under `cases/` automatically.

The current `golden.csv` files (`zmin=0.4 zmax=0.95 zstep=0.5`, `p=2`,
`b=0`, `muratio=1`) were generated by building and running commit
`3177799` (`Change build system to CMake` — the original, pre-refactor
code, from before this test harness even existed) in a separate worktree,
using the same `KCBK_fit_3/proton.dat`/`TAvalues_Pb_Heikki.dat` inputs
committed later in `bed53d1`.
